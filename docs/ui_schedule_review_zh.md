# UI 与日程管理审查报告

审查日期：2026-07-06

## 结论

Paneloom / 格织（旧名 Storyboard Genie）当前方向是成立的：它已经不是单纯的图片生成器，而是一个围绕“剧本到漫画分镜到图片资产再到发布反馈”的桌面生产工具。对于你描述的需求，也就是根据剧本做漫画分镜、生成单张图或漫画网格图、再用于后期解说漫画视频素材，它的主链路已经基本对齐。

它现在更适合继续做桌面端，而不是马上做手机版。原因是：剧本编辑、批量图片生成、文件导出、参考图管理、日程复盘都更依赖大屏、键盘、本地文件夹和稳定工作流。手机端可以以后做查看或轻量记录，不适合作为当前主版本。

## 当前 UI 是否合理

整体 UI 是可用的桌面工作台风格，信息密度偏高，但这符合创作生产工具的定位。它没有做成营销页，也没有把核心能力藏起来，用户进入项目后能直接做事。

合理的部分：

- 左侧导航把项目、分镜、日程、设置拆开，符合桌面工具习惯。
- `Storyboard` 页把剧本拆分、Project Bible、参考图、生成、导出、漫画预览放在同一工作流里，适合连续操作。
- 图片比例选择已经前置到生成前，符合“未来要发到不同平台”的需求。
- 单张图和漫画网格两种产出形态都存在，适合后续做解说漫画视频素材。
- `Schedule` 页已经覆盖计划、任务状态、工作时间、社媒反馈、周/月复盘，方向正确。

需要注意的部分：

- 当前界面语言是英文。如果最终主要给中文用户使用，发布前应统一中文化。
- Storyboard 页面功能很多，对新用户会有一点密集；但作为桌面工具可以接受，后续可以加更清晰的步骤状态。
- 生成图片和批量生成仍是同步体验，长任务时缺少明确队列、取消和重试视图。

## 日程管理是否合理

日程管理的产品设计方向是合理的。它把内容生产拆成三层：

1. 目标层：什么时候发布、每周更几次、每天有多少时间。
2. 执行层：每天做哪些任务，每个任务处于什么状态。
3. 复盘层：实际花了多久、哪里卡住、发布后反馈怎么样。

这个设计符合漫画内容生产的真实情况，因为真正影响产出的不是单次生成图片，而是能不能持续稳定地完成“写、拆、画、修、发、复盘”。

本次检查后已经修正的关键问题：

- 默认目标发布日期从“今天”改为“14 天后”，避免新用户一生成计划就得到很奇怪的当天截止排期。
- `Due` 区域现在显示今天及以前未完成任务，避免逾期任务被隐藏。
- 工作流步骤现在可以在界面编辑，不再只是后端隐藏字段。
- 时间记录增加了 Notes，可以记录卡点和复盘线索。
- 社媒反馈增加了发布日期、主观判断、完成率、备注等字段。
- 记录时间和反馈成功后会清空表单，减少重复录入错误。
- 生成计划区域增加了提醒：重新生成会替换当前任务列表。

## 日程模块仍然缺失什么

这些不是马上不能用的问题，但属于进入 `.exe` 稳定版前应优先考虑的能力：

- 缺少日历视图：现在是任务列表，不是周历或月历，看时间分布不够直观。
- 缺少拖拽改期：任务日期、标题、估时虽然后端支持更新，但前端列表目前主要只能改状态。
- 缺少自动重排期：当任务逾期、时间不足或反馈变化时，系统还不会主动重新计算计划。
- 缺少 AI 复盘：现在复盘是规则型总结，还不能真正分析“为什么这条内容表现好、下一条该怎么调整”。
- 缺少平台实验维度：虽然能记录平台和比例，但还没有把钩子、封面、标题、发布时间做成结构化实验字段。
- 缺少趋势图：周/月复盘没有折线图、阶段耗时占比图、平台表现对比图。
- 缺少提醒机制：没有本地通知、今日开工提醒或临近发布时间提醒。
- 缺少导入导出日程：无法把任务和反馈以 CSV 方式导入导出给其他工具。

## 现阶段最优下一步

建议先不要打包 `.exe`，先用真实项目跑一轮闭环：

1. 用一个 6 到 8 格短篇漫画项目测试。
2. 在 Settings 配好一个文本模型和一个图片模型。
3. 从剧本拆分分镜。
4. 选择 9:16 和 2:3 两种比例生成。
5. 导出一组单图和一张漫画网格 PNG。
6. 在 Schedule 里生成两周计划。
7. 每天记录实际用时。
8. 发布后记录反馈。
9. 做一次 Weekly Review。

如果这条链路能稳定跑通，再做下一轮功能增强：

- 任务编辑和日历视图。
- 生成队列和失败重试。
- AI 复盘与自动重排期。
- 设置项安全处理。
- Windows `.exe` 封装。

## 是否符合你的产品方向

符合。它现在的产品方向可以定义为：

“面向桌面创作者的漫画分镜与发布节奏管理工具，用于把剧本拆成可生成的漫画镜头，输出单图或网格图，并记录后续发布反馈，帮助持续优化内容生产。”

这个定位比“图片生成器”更有价值，也更贴近你的真实工作流。它暂时不需要做完整手机版；如果未来做移动端，更合理的是做一个轻量伴随端，用来查看今日任务、记录时间和填写发布反馈，而不是承担完整分镜和图片生成。
